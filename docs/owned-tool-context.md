# Owned tool context and selected workspace

The attached session's built schema snapshot exposes an opaque context ID and schema revision. Main/runtime identity and profile isolation are distinct from a human effect or target grant. Discovery never rebuilds a frozen conversation schema or grants execution.

When the frozen schema contains `tool_call`, context custody also captures the selected profile's deferrable registrations and inline execution owners privately. Selection uses the existing enabled/disabled/role toolset rules before availability filtering; readback does not invoke check functions or publish deferred schemas/manifests. A registration replacement retires old context even with identical schema and handler, and an observed A→B→A cannot revive it. This is an admission fence, not provider readiness, connector batch qualification or complete deferred target/effect coverage. Frozen public schema bytes and revision remain unchanged when only these private owners change.

During a parent-bound registry `tool_call`, the existing dispatch binding carries the parent's captured registration map through deferred resolution. The real registry checks the selected inner entry, handler, schema/effect digest, target resolver and profile under its lock immediately before choosing the captured handler. An inner name missing from that capture is refused rather than adopted from later discovery. A replaced inner entry returns an error without running its handler; the outer durable attempt remains terminal and metadata-only replay does not redispatch it. Connector batches and inline deferred routing are separate qualification boundaries.

The local stdio MCP qualifier uses the installed SDK and a real fixture server under two profile homes, with the same server name and different synthetic `.env` markers. Actual discovery/registration, owned deferred calls A→B→A and inbound JSON-RPC records prove three read-only calls and no foreign/replay/write-capable calls. Untrusted write probes are denied before transport; both owned server PIDs disappear after scoped shutdown. SDK 2.x annotation objects use `read_only_hint`, read through the existing SDK-version field helper; cached wire dictionaries retain `readOnlyHint`. This preserves the existing trust policy and is not independent validation of a server's annotation, approved write effects, real external accounts, HTTP/OAuth/reconnect or Web/Desktop screen qualification.

MCP tool-only calls recheck their existing authority after consent, before acquiring a connection/scheduling each attempt, and on the async side after the server RPC lock. Resource/prompt utilities use the same pre-connection and post-lock check. A retired owner fence returns an error without recovery retries or breaker penalties for that pre-dispatch refusal. Unbound ordinary MCP calls keep their existing policy. The real stdio qualifier uses a synthetic once-answer callback: an approved write-capable probe crosses the wire once; changing the live profile before that answer prevents the probe from crossing the wire. Metadata-only replay does not ask again or send again. Actual resource-list RPCs also succeed. This is a cwd/terminal-policy fence and owned cache-generation mechanism, not a complete effect/target manifest or proof of every backend migration.
