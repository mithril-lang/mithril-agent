# Original Mithril schedule custody client (draft)

This owned plugin connects the original Agent to the account-bound custody protocol at `api.mithril.fund`. It adds an internal/operator CLI command, not a model tool, new scheduling parser or alternate Schedules screen. Original cron/once/interval definitions and microsecond occurrence identities are passed unchanged.

Enable through the existing plugin configuration. The selected profile's existing `MITHRIL_API_KEY` is resolved through `agent.secret_scope`; do not add behavioral environment variables or copy credentials between profiles. Production requests use the fixed Mithril API origin. HTTP loopback origins exist only for local qualification. Ambient proxies and redirects are disabled.

The Desktop prerequisite can invoke the owned `bootstrap.py -p <profile> --stdin` directly with the same bounded `{owner, prepare}` envelope. It resolves the existing profile, verifies fixed-origin account status before proposing enablement, and submits only this bundled policy's selection through the existing PM transaction with config CAS. Other selections, entries and grants are preserved. Explicit disabling or a winning user/project/entry-point override is refused. It then rechecks provenance and runs the original source preparation; failed admission or preparation is not a synchronization or execution receipt. After new admission, the required marker is durable before the existing plugin activation path notifies the running Desktop/gateway. Open conversations retain the generic deferred prompt/tool behavior; an unavailable runtime is not an execution receipt. Already-enabled policies do not trigger repeated activation on every background poll. This adds no core CLI special case or user migration screen.

Local qualification covers actual discovery, original source/policy persistence across A/B/A homes, malformed direct-process requests and the production PM submission/refusal boundary. The additional publication test uses the independent real PM worker with an already-current dependency environment: A/B/A profile configuration commits preserve comments, unrelated selections/grants, model settings and exact BOM/CRLF original source bytes. A concurrent explicit disable fails config CAS before policy preparation. The real activation path is called after required policy persistence only on the first admission per profile; no user's running runtime is contacted in this isolated fixture. The Python 3.14 canonical bootstrap/publication/custody suite passed 23 tests before the activation addition, and the changed bootstrap/publication suite passed 15 afterward. Dependency rebuilding, live runtime activation, production API access, reviewed installer pins and installed-client qualification remain separate requirements.

`hermes mithril-schedule-custody --stdin` reads a bounded JSON envelope with `owner` and `command`. Commands are the exact API `status`, `select`, `claim` or `transition` payloads. Caller-supplied executor or credential identities are not supported. Receipts must match the expected account/profile/operation and exact result schema before they are returned. Replayed starts return `changed: false`; a lost acknowledgement returns an unknown outcome without retry. No script, tool or model is executed by this command.

Qualification covers real plugin discovery across A/B/A homes with different scoped credentials, real HTTP requests, redirected/lost acknowledgements, foreign/extra receipts, replayed starts, precise original timestamps and bounded requests. The API's separate workerd D1/R2 qualification covers actual server custody and authentication.

The plugin now registers the generic `cron_execution` policy consumed by the original scheduler before its dispatch counter, script, agent and delivery effects. A private per-attempt `_execution_binding` must name this policy and bind the exact original job digest (excluding attempt-local fields), account and original occurrence/operation/source/executor revisions. These are main/worker metadata, not an alternative scheduling parser or user migration screen. The existing native execution ledger remains authoritative for whether the complete original run finished. Only a fresh cloud claim followed by a fresh running transition admits the downstream run. Missing policy, malformed binding, retained claims, lost acknowledgements and foreign receipts cannot fall back to an unguarded run. Unknown or failed original outcomes retain the cloud unknown lane; known completion updates the same operation without rerunning work.

Qualification executes a real original `no_agent` shell job and writes a real effect file, under A/B/A profile homes with different credentials and a local HTTP custody peer. Replayed starts, retained claims, lost start acknowledgements, foreign receipts and unloading the policy leave the effect file unchanged. The existing API D1/R2 qualification remains separate from this HTTP peer test.

The scheduler-policy regression fails when the original unguarded body bypasses custody (the script runs without the required HTTP claim/start/completion), and passes after restoring the gate. The focused plugin, middleware-failure/ownership, compatibility and original Cron execution/no-agent suite passed 163 tests. Ruff and Python compilation passed. The private job digest is canonical UTF-8 JSON with sorted keys and compact separators, excluding only `_execution_binding`, `execution_id`, `_scheduled_instant`, `run_claim`, `fire_claim` and `pending_slot`; other authored fields and metadata are bound. Producers must not reuse this digest across changed jobs.

Automatic Native lifecycle production of these private bindings, reconciliation across original source/resource changes, unknown-result reconciliation, background synchronization, shared original Schedules mounting, current-main publication and installer qualification remain required. No existing job is activated by enabling this draft policy; profiles without a durable required marker keep their original path, and original source restoration still refuses unbound activation. Never infer scheduler activation from a successful CLI status/claim. API migration0050 and authenticated route publication remain separate delivery gates. Existing scopes are not silently upgraded.

Binding presence is mandatory even when its value is damaged: an explicit null, false, string, list, empty object or unnamed policy is refused before original effects and records a failed execution with suppressed delivery. Only an absent binding retains the original unbound path. A real shell-effect regression failed on the previous null fallback and passes after distinguishing presence from value. The canonical `scripts/run_tests.sh` runner, with an explicit test interpreter, clean credentials and per-file subprocess isolation, passed 164 tests across the six custody, middleware and original Cron files; Ruff and whitespace checks passed. This verifies damaged-binding refusal and preserves ordinary original jobs, not automatic source binding or production activation.

The internal CLI also accepts `{owner, binding}` after the Native producer has published the portable source and restored its resources. The binding anchor contains `profile`, `sourceRevision`, `sourceDigest`, `authorityRevision` and the exact original file's `nativeVersion`. It verifies the current cloud authority revision and persists a private profile-scoped inventory under the original fire fences and jobs lock, with source and policy-state compare-and-swap. It leaves `jobs.json` bytes unchanged. The original scheduler resolves this inventory in each fresh worker process. A required marker is written before the inventory so missing/corrupt state, new unbound jobs, changed authored definitions or an unloaded policy cannot restore unguarded effects. The per-occurrence server claim still verifies the portable source; a status receipt alone does not authorize execution. Operational bookkeeping does not invalidate the stable authored definition, while unknown authored metadata remains bound.

It covers recurring microsecond instants and manual execution using the original ledger's durable claim time. Missing storage, changed definitions, concurrent source/policy revisions and plugin unload refuse effects. This is local qualification; the HTTP peer does not prove production D1/R2 publication, automatic Native mounting or multiple-device execution.

Before automatic restoration or executor selection, the internal CLI accepts `{owner, prepare: {profile, nativeVersion}}`. It verifies the account through the fixed authenticated status route, then requires the generic policy lane under all original inventory fire fences and the strict jobs lock. A missing original file uses a null CAS. Preparation preserves current source bytes and existing policies; it does not select an executor, grant permissions, or execute a job. A new enabled/scheduled record can then restore byte-for-byte through the original source transaction: it has no unguarded execution path while its policy is missing. Legacy profiles without a required policy still refuse active new records, and damaged required storage refuses restoration.

Passive replicas may persist original source bindings at the current authority revision. Only the existing fresh claim/start protocol admits effects for the selected credential; source synchronization must not depend on being that executor. Missing/corrupt policy stores, stale source/store CAS and a real process holding an original fire fence are separately exercised.
